TECHNICAL NOTE / GO CONCURRENCY

Go · 并发原语 · 缓存治理

singleflight：
用一次查询合并一批并发请求。

缓存击穿时，同一个 key 的多个并发请求不必各自访问数据库。singleflight 让其中一个请求真正执行，其余请求等待并共享结果。

golang.org/x/sync/singleflight 缓存击穿 请求合并 Group.Do

OVERVIEW

先记住一句话

singleflight 是 Go 官方扩展库里的一个小工具，核心作用是：同一个 key 的多个并发请求，只让其中一个真正执行，其余请求等它跑完后直接分享结果。

包名很直白：一批飞行中的请求合并成一次（single flight）。它不是缓存，也不会保存结果；它只负责合并同一时刻正在执行的重复调用。

THE PROBLEM

它要解决的是缓存击穿

某个热点 key 的缓存突然失效，瞬间来了几百个并发请求。大家发现缓存里没有，全部转头去打数据库，数据库压力被瞬间放大——这就是缓存击穿。

没有 singleflight

100 个并发请求同时 cache miss → 100 次相同的数据库查询同时发出，资源浪费且数据库压力被放大 100 倍。

有 singleflight

100 个并发请求同时 cache miss → 只有 1 次真正的数据库查询，其余 99 个原地等待，结果返回后一起共享。

CORE USAGE

核心用法：Group.Do

var g singleflight.Group

func getData(key string) (interface{}, error) {
    v, err, _ := g.Do(key, func() (interface{}, error) {
        return queryFromDB(key)
    })
    return v, err
}

关键就是 Do(key, fn)：只要传入的 key 相同，并发调用时只有第一个 goroutine 会真正执行 fn，后来的调用会阻塞等待。第一个调用完成后，大家拿到同一份结果，或者同一个 error。

UNDER THE HOOD

内部如何合并请求

它的核心并不复杂：用一个正在执行的调用表，加上等待机制，把相同 key 的请求汇聚到同一次执行上。

01

Group 内部维护一个 map[string]*call，key 是业务传入的 key，value 是这次“飞行中”的调用状态。

02

第一个请求进来，发现 map 里没有这个 key，创建一个 call，内部用 sync.WaitGroup 做同步，登记后真正执行函数。

03

后续相同 key 的请求进来，发现 map 里已经有了，直接 wg.Wait() 挂起，不重复执行函数。

04

第一个请求执行完毕，把结果存起来，调用 wg.Done()，同时把这个 key 从 map 里删掉，不影响下一轮请求。

05

所有等待的请求被唤醒，读取同一份结果返回。

BOUNDARIES

使用时要注意的边界

  • 结果是共享的：如果业务函数返回的是可变对象，多个调用方拿到的是同一个引用，谁改了都会影响别人，最好返回不可变数据或做拷贝。
  • error 也会被共享：第一个请求失败了，所有等待者拿到的都是同一个 error。通常这是期望行为，但要在业务上想清楚。
  • 不是分布式的：singleflight 只在单个进程内生效，多副本部署时每个实例还是会各打一次数据库，真正的分布式合并要靠分布式锁或其他机制。
  • DoChan 的取消行为：使用 DoChan 时，如果调用方提前放弃接收结果，要注意 goroutine 泄漏和资源释放的时机。

API CHOICES

三个方法怎么选

Do(key, fn)

同步阻塞等结果，最常用，逻辑简单直接。

DoChan(key, fn)

返回 channel，适合需要配合 select 做超时控制的场景。

Forget(key)

主动把某个 key 从记录中移除，让下一次调用重新真正执行，而不是复用旧结果。

WHEN TO USE

什么时候值得使用

  • 缓存失效瞬间的高并发查询：缓存击穿的标准解法之一。
  • 多个请求最终会打到同一个下游资源，且结果对所有请求都是一样的，比如按 ID 查详情、拉取配置。
  • 下游调用成本高，比如数据库、外部 API、重计算，而并发重复调用的收益几乎为零。

CONCURRENCY TEST

用一个小程序验证效果

下面的程序模拟 5 个 goroutine 同时用同一个 key 请求，观察底层函数到底被执行了几次：

package main

import (
    "fmt"
    "sync"
    "time"

    "golang.org/x/sync/singleflight"
)

func main() {
    var g singleflight.Group
    var callCount int32
    var mu sync.Mutex

    fetch := func() (interface{}, error) {
        mu.Lock()
        callCount++
        mu.Unlock()
        time.Sleep(200 * time.Millisecond)
        return "结果来自数据库", nil
    }

    var wg sync.WaitGroup
    for i := 0; i < 5; i++ {
        wg.Add(1)
        go func(id int) {
            defer wg.Done()
            v, err, shared := g.Do("same-key", fetch)
            fmt.Printf("goroutine-%d 拿到: %v, err: %v, 是否共享结果: %v\\n", id, v, err, shared)
        }(i)
    }
    wg.Wait()
    fmt.Println("真正执行 fetch 的次数:", callCount)
}

预期结果

5 个 goroutine 都能拿到“结果来自数据库”，但 callCount 最终只会是 1。只有第一个 goroutine 真正执行了 fetch，其余调用复用了同一次调用的结果。

TAKEAWAY

合并重复请求，
把压力留在边界之外。

singleflight 不是缓存，而是缓存 miss 之后的一道并发闸门。
